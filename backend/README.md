# Channel3 catalog proxy

`index.js` is the source of the existing `AnoX-Channel3-Catalog` Lambda. `build-template.cjs` embeds it byte-for-byte in `cloudformation.json`, preserving the `Channel3Function` logical ID, physical name, Node 24 runtime, timeout and memory. Existing search/Nike/CJ routing remains unchanged. This staged template adds one dedicated Channel3 detail route, integration and scoped invocation permission to the existing HTTP API.

Generate with `node backend/build-template.cjs`; verify source/template identity with `node backend/build-template.cjs --check`. Run the network-free backend tests with `node --test tests/backend*.cjs`. This directory performs no deployment automatically.

## Public contract

`GET /catalog/search` accepts either nonempty `q` or a supported `section`, `limit` from 1 to 24 (default 24), optional `page_token`, and optional `filters` JSON. Unknown or duplicate parameters are rejected. Search text is NFC-normalized, trimmed, and consecutive whitespace collapsed; case is retained. Its normalized length is at most 100 characters. C0/DEL controls and malformed UTF-16 are rejected. A missing/empty search must select `section=featured` explicitly; it never silently becomes another query.

Sections: `featured`, `men`, `women`, `shoes`, `clothing`, `beauty`, `accessories`, `sports`, `brands`. Their fixed backend queries are versioned in `SECTIONS`. Only the requested section runs. These sections use product search, not separate upstream brand/category APIs.

The supported filter subset is `conditions` (`new`, `used`) and `availability` (`InStock`, `OutOfStock`), each containing one or two entries. Arrays are sorted and deduplicated; object-key order is immaterial. Unknown fields/values fail before upstream access. The frontend's other display filters remain local.

Continuation tokens retain exact text, including surrounding spaces and punctuation, and are capped at 8,192 characters. They are accepted only when issued for the identical provider/mode/section/query/filter/limit context. A chain has a 30-minute lifetime and a 500-source-record traversal limit, including source records discarded during sanitization. Local unknown/mismatched tokens return `400 CURSOR_INVALID`; expired mappings return `410 CURSOR_EXPIRED`. Upstream 400/404/410/422 on a continuation returns `410 CURSOR_INVALID`: this means the continuation cannot be used, not that Channel3 documented a particular expiry. No failure silently restarts at page one.

Successful responses are `{provider:'channel3',data:{products,next_page_token},fetchedAt,expiresAt}`. An exhausted page has a null token. Only bounded product fields, USD offers linking to `buy.trychannel3.com`, and one primary image from `cdn.trychannel3.com` are retained. The proxy never establishes purchase eligibility, stock reservation or payment authority.

## Product detail contract

`GET /catalog/channel3/products/{id}` accepts only exact `option_<name>=<label>` query parameters. IDs use1–80 ASCII letters, digits, underscores or hyphens. At most8 options are accepted; names and labels are bounded to60/80 characters, preserve exact case/spacing, reject controls, malformed encoding, duplicate parameters and prototype-related names. The upstream call is the official free `GET /v1/products/{id}` with fixed `country=US`, `currency=USD`, `language=en`. No client-selectable upstream URL, locale, credential or cache bypass exists.

Responses are `{provider:'channel3',data:{product},fetchedAt,expiresAt,status,error,selectionMismatch}`. The product is a bounded allowlist of the official Product shape, independently sanitized from catalog cards. It retains up to64 original gallery images,60,000 description characters, brands, category, materials, key features, structured attributes, up to64 offers, and real option/selected values. Oversized collections or payloads are rejected rather than silently truncated. Only Channel3 CDN and attributed-buy hosts are retained. Unknown price, dimension, availability, condition or commission values remain null; no stock count or offer identifier is invented. Exact cent-representable USD prices up to$1,000,000 are retained; unsupported fractional prices/currencies remain unknown.

`variants.selected` is the effective upstream choice. `selectionMismatch` contains `{name,requested,effective}` for each requested option the provider relaxed or omitted. Consumers must acknowledge it and require current matching selections before quoting. Values with another `product_id` navigate to that product. An offer's merchant domain and condition identify the selected merchant listing; rotating attributed URLs are metadata, not persistent offer IDs. Multiple offers sharing that identity must remain ambiguous to the quote service.

The browser's `getChannel3Product(id,{options,signal})` returns the separate `anox.product-detail/1` model. See `tests/fixtures/channel3-detail.cjs` and `tests/adapter-detail.cjs`. It includes full images, normalized offers/options, effective selected values, freshness and mismatches. `stock` is always null and `purchasable` always false; detail retrieval conveys neither merchant authorization nor inventory reservation.

The commerce runtime invokes this Lambda directly with exactly `{operation:'commerce.product',productId,options?}` using its scoped IAM permission. Extra event keys, including HTTP metadata, are rejected. API Gateway requests cannot become private operations. Success returns the fresh envelope directly; safe errors are `{statusCode,error}` without data. This internal path never accepts presentation fallback. There is no public quote-refresh flag and no new HTTP route for the internal operation.

## Cache and failure behavior

SHA-256 keys include contract version, provider, mode, section, normalized query, canonical filters, limit and cursor. No raw query or cursor is stored in the key. Cached payloads contain the necessary next token, with table access restricted to the dedicated runtime role. Search freshness is five minutes; discovery freshness ten. Application timestamps enforce expiry independently of asynchronous DynamoDB TTL cleanup. Responses are never served stale.

Strongly consistent reads plus conditional 25-second leases coordinate different Lambda instances. One process also coalesces matching promises. The owner rechecks the cache after acquiring a lease, then atomically stores the page/cursor mapping and deletes its owned lease. Waiters poll for at most six seconds; a failed winner is not automatically retried by a waiter. A later deliberate request can retry. Abandoned leases expire, and conditional publication prevents a previous owner writing after lease loss. Cache failures fail closed without bypassing the cache. DynamoDB transport is bounded to 1.5 seconds per operation; the SDK may retry an AWS operation, but an upstream Channel3 POST is never automatically retried.

Upstream requests have a ten-second timeout, reject redirects and non-JSON content, and read at most 2 MiB. Sanitized responses are capped at 300 KiB, below DynamoDB's item limit including metadata. Malformed responses/errors are not stored as successful pages. Product identities are not fabricated.

Detail responses are capped at256KiB. Each later detail view, reselection or internal quote refreshes upstream. Identical requests coalesce only while the upstream retrieval is still in progress. The30-second Dynamo exchange may serve only a request that began before its result was fetched. Each waiter is checked independently, including local waiters joining during distributed reads; an ineligible waiter fails safely. Late arrivals during a slow durable write wait for that operation and start a new retrieval.

The same transaction publishes a one-hour presentation row that contains no offers, prices, attributed buy URLs or variant availability. On a refresh/budget/contention failure the public route may return this as `status:'presentation_only',error:'DETAIL_REFRESH_UNAVAILABLE'`; quotes cannot. A provider404 does not use fallback. Missing/expired fallback produces an error. Cache corruption and infrastructure failure fail closed. Dynamo TTL is cleanup only; application timestamps enforce both lifetimes.

Phase1 paid search caches remain5/10-minute snapshots. Current provider guidance says prices, availability and offer URLs must refresh before display; those existing cached card fields are not a provider-approved freshness guarantee. A written provider allowance or separately approved card strategy is a release prerequisite. The implementation does not add24 detail calls per grid. See `docs/commerce/channel3-contract.md` for sources and limits.

## Usage budgets and monitoring

No new paid allowance is enabled by default. `BudgetMonth` is empty, free/paid monthly search allocations and search/detail daily/monthly caps are zero, and `PaidUsageEnabled` is false. Each class requires explicit nonzero allocation and a current UTC month. The shared daily cap defaults to1,000 requests and the shared second cap to5; neither authorizes a request on its own. A positive paid credit allocation also requires explicit opt-in. These defaults intentionally make uncached work unavailable until the operator approves a reconciled budget. Fresh cache hits still work without new reservations.

The documented provider allowance is1,000 free credits **per month**, not per day. Public list pricing is$0.007/additional credit; search and lookup are each one credit, while product-detail retrieval is zero-credit. AnoX uses search and product retrieval, not lookup. The actual account tariff, remaining credits, billing timezone and other consumers have not been verified. See [the cost policy](../docs/remediation/channel3-cost.md) for all parameters, sources, accounting assumptions and renewal instructions. No local counter is a provider invoice or a guarantee that a request is free.

Before each upstream attempt, one Dynamo transaction reserves month/class, day/class, shared day and shared fixed second counters. Period/class identities survive configuration changes. Month rollover requires a newly approved allocation; it does not automatically assume another free allowance. Non-numeric/negative counter values fail their conditional write. Reservations are conservative: failures/cancellations are never refunded, SDK retries reuse their transaction token, and conditional failures cannot partly increment another counter. A delayed reservation is rejected once its original second ends. The fixed window permits a boundary burst of up to10 requests at the default5/s.

Exhaustion returns429; missing/unrenewed/malformed policy or storage failure returns503. None can fall through to unbudgeted HTTP. Daily/provider quota and request rate are separate from paid credits, and these service counters cannot account for other applications using the provider key. Configuration in the same month is a total cap over existing reservations, not an additive allowance. Never delete counters or roll back their table contents to recover capacity. Disable upstream work and reconcile consumed provider usage before any restoration/migration or limit renewal.

CloudWatch EMF distinguishes `search_credit_request` and `product_detail_request` from cache/upstream failures, detail coalescing, fallback, `budget_exceeded`, `rate_limited`, and `budget_error`. Request counters fire immediately before transport; they neither classify provider-invoiced paid/free credits nor equate product detail with paid lookup. Reservations can exceed HTTP attempts after cancellation. No query, cursor, cache key, body, credential, header or customer data is logged. Staged alarms cover usage, allocation denials, upstream/storage failures. Daily alarms use24-hour CloudWatch periods while enforcement uses UTC calendar days. An existing authorized SNS topic and an operational owner are required for notifications; absent `ExistingAlarmTopicArn`, alarms are visible only.

## Deployment boundary

The template retains the existing on-demand DynamoDB cache table and dedicated role. It does not modify the CJ `AnoX-Products` table or the shared `AnoX-Catalog-API-Role`. The table is retained on stack deletion/replacement, with staged deletion protection and point-in-time recovery. It contains spend-control counters as well as disposable cache data and must not be casually cleared or rolled back; it is not an order store. The dedicated role has only Get/Put/Delete/Update on that table (including the corresponding transaction item operations), GetSecretValue on the exact configured secret ARN, and stream/write permissions on the existing log group. No separate `dynamodb:TransactWriteItems` IAM action is needed. The existing log group must remain present; this template does not recreate or import it.

The deployed Lambda lazily resolves its configured secret with the AWS SDK and caches it in memory for five minutes. It supports the existing raw string, `apiKey`, `api_key`, or `key` formats. Agent tooling and tests never retrieve its value. Tests use synthetic strings and injected transports. The Node 24 Lambda runtime supplies AWS SDK v3 clients; local unit tests do not require them or AWS credentials.

CloudFormation synthesis/validation is separate from deployment. Only the deployment operator can establish actual role propagation, runtime SDK availability, secret access, table writes and HTTP API behavior. Browser CORS is preserved as `https://anox.app`; CORS itself is not authentication or a server-side abuse limit.

The generated template exceeds the51,200-byte `TemplateBody` request limit and must be supplied through an approved private S3 `TemplateURL` (the template maximum is1MiB). No artifact bucket is provisioned automatically. Review the exact generated file, its checksum and a non-executed change set before separately authorizing deployment. Preserve `ExistingHttpApiId`, verify the new route does not already belong to another stack, and confirm the existing stage deploys route changes (or create a reviewed stage deployment when auto-deploy is off). Verify API-level CORS permits the production origin and GET; adding this route does not change the existing API's CORS/stage settings. The new Lambda permission restricts API Gateway to this account/API and `GET /catalog/channel3/products/*`.

After authorized deployment, verify one bounded live detail request, exact variant selection/mismatch,404, concurrent detail calls, fallback, budget rejection and the commerce IAM-only invocation in staging before release. No new detail endpoint, quota transaction, checkout integration or financial operation has been verified against production in this work. Roll back the catalog stack to the saved prior template/code and remove only this stack's detail route/integration/permission/alarms; retain cache data and existing routes. The frontend should be rolled back with the backend so it does not depend on a removed detail route.
