# AnoX critical engineering release assessment

Assessment assembled October 13, 2026. **Release verdict: HOLD.** The reviewed source contains a useful catalog, product, cart, fresh-quote and owned-order foundation. It does not provide an operational merchant checkout. No merge, deployment, production configuration change, payment, merchant purchase or secret-value retrieval was performed by this remediation review.

The review resumed from `7958718de6d859da1c809abef7b98e012a857973` on `feat/anox-commerce-foundation`. This document describes the remediation delta; the exported build manifest supplies the exact final commit and file hashes. The completed baseline was preserved, not rewritten. The final combined verification is recorded in [validation.md](validation.md); historical counts in older commerce documents describe earlier revisions.

## Executive assessment

The source boundary is intentionally conservative: only server-fetched product/merchant/variant snapshots can enter a quote; a quote does not reserve stock or guarantee a payable delivered amount; a checkout attempt stays `blocked`; the fee is one conditional **500 USD cents per successfully completed order**. No fee is collected by the new foundation. Browser prices, callbacks and local storage cannot confirm payment or merchant acceptance.

The remediation corrected demonstrated product-selection, response-freshness, cost-policy and client-contract defects. Independently reviewing those fixes also found a dropped variant-selection intent and a missing budget-error metric; both received regression coverage and corrections. There was no demonstrated new source-level P0 access bypass in the scoped commerce implementation. Open P0 release gates remain: backend routes are missing, reserved concurrency cannot be allocated under the captured quota, and authorized merchant purchasing/payment/delivered-cost capabilities are unavailable. These gates are not waived by unit tests.

P1 limitations also prevent a production-readiness claim: Channel3's cached card-price policy needs resolution, deployed operations lack the staged usage controls/notifications, real-service performance and transaction behavior remain unverified, and future financial operations lack a complete recovery/retention arrangement. The existing sandbox payment infrastructure remains separate and unchanged; it must not be used as a fallback for this frontend.

## Legacy trust boundary and coexistence

The processed stack-source inspection covers Checkout Core/Auth, Payment Webhook/Read, Account API, Shipping Core and Channel3. `legacy-template-inventory.json` records successful reads and source sizes. Function metadata hashes are retained separately. Manual Lambda drift was not excluded; do not call these findings a deployed-byte attestation.

- **Checkout Core/Auth:** sandbox-only secret-key validation and fixed server catalog prevent browser arbitrary-price authority in that source. They do not implement the new merchant lifecycle or fixed fee. Public `/checkout` remains public; authenticated wrapper creates then links ownership. Retry/partial-state concerns are LEG-01; no legacy source or configuration was changed. New transport rejects these paths instead of falling back when `/commerce` is missing.
- **Legacy webhook:** source verifies raw HMAC with a five-minute tolerance, accepts test mode, matches stored amount/currency/session and atomically records receipt/payment/order state. Paid state cannot be downgraded by older events. It handles a limited checkout-session lifecycle, not operational merchant acceptance, refunds, disputes or the new commerce payment binding. Payment confirmation must never mean merchant purchase confirmation.
- **Payment Read/Account API:** source checks JWT subject and order ownership before payment/order/tracking output; order linking requires verified matching email and a conditional owner assignment. The review did not demonstrate a cross-customer read bypass. Real two-identity tests remain unperformed. Gateway cryptographic enforcement and source ownership checks are different layers.
- **Shipping:** sandbox EasyPost workflow gates rates on paid legacy orders and real supplied parcel dimensions/weight. It is not a fresh landed-cost quote before purchase. Existing account availability does not authorize production labels, shipments or duties estimates.
- **IAM:** inspected role policies scope commerce to its own table/logs and the named catalog function; it receives no Stripe/Channel3 secret access or legacy table access. Catalog secret permission remains server-side and ARN-scoped. Legacy catalog can also read the Channel3 secret, so runtime budgets cannot promise account-wide spend control. Some legacy basic logging policies use wildcard resources; this change does not expand them. Absence of a permissions boundary is not proof of an effective-access vulnerability; full organizational/session/resource-policy analysis remains outside this evidence.
