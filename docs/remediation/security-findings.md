## Trust boundary findings and evidence

- **Authentication:** `backend/commerce/index.js:10` accepts customer authority only from API Gateway JWT authorizer claims and rechecks exact issuer, audience, ID-token use, nonempty bounded subject and unexpired exp. Cryptographic signature/JWKS validation belongs to the existing HTTP API JWT authorizer; the handler does not accept a body/header-supplied owner. New `tests/commerce-service.cjs:169` tests all six private route shapes against wrong issuer/audience/type, empty/invalid subject and expired/missing expiration before any persistence access. This is a handler-claims test, not a real Cognito test.
- **Ownership:** `backend/commerce/store.js:7` hashes the verified subject into a customer partition. Quote lookup, attempt creation, order list/read, cancellation and refund checks never accept customer partition keys from the browser. Missing and foreign-owned records both return404. Order cursors retain the verified owner's partition; public order output omits arbitrary stored fields. Existing service/persistence tests cover foreign-owner access and corrupted public records.
- **Input and money authority:** `backend/commerce/validation.js:19` only permits the documented identifier/merchant/condition/options/quantity inputs. Browser price, total, owner and unsupported fields are rejected before hydration. `backend/commerce/quote.js:32` revalidates the exact requested product, merchant, condition, selected options and stock from private fresh hydration. Ambiguous merchant offers and relaxed variants fail; unknown/out-of-stock remain blockers. No synthetic stock or quantity reservation exists.
- **Idempotency and concurrency:** `backend/commerce/store.js:13` binds a conditional claim to owner, operation and canonical payload hash; token/lease checks fence takeover and completion. `store.js:31` commits the result, resource and audit atomically. A lost successful transaction reply cannot create another quote or audit on retry (`tests/commerce-service.cjs:203`). Blocked attempts replay exactly and reject a modified payload under the same key (`:212`). Expired quote attempts remain rejected before a new attempt is persisted; a replay of a previously blocked attempt remains blocked.
- **Errors and privacy:** `backend/commerce/index.js:74` returns only known public CommerceError messages; untrusted diagnostics map to generic503. Logs contain outcome/status only, responses use no-store. The commerce role has no Channel3/Stripe secret permissions and no legacy table access. CORS is a browser restriction, not authorization; server ownership checks remain mandatory.
- **Order/payment state:** `backend/commerce/orders.js` prevents unverified confirmation and unsupported status jumps. `webhooks.js:25` validates payment reference, amount, currency, environment, account and metadata; `store.js:54` atomically checks the active payment identity and current order version with binding/receipt/audit writes. Prior regressions for same-amount old payments and fulfillment-version changes remain passing. Payment success alone never confirms merchant acceptance or recognizes the $5 as earned revenue. HTTP webhook remains disabled, with no route or credentials provisioned.
- **Infrastructure:** regenerated commerce template retains one new encrypted/PITR/deletion-protected retained table, exact catalog invocation IAM, bounded function, existing JWT authorizer reuse and only namespaced routes. No shared API, legacy payment table or authentication resource is imported. API-level Idempotency-Key preflight still requires separately approved settings; handler CORS headers alone cannot supply it.

## Financial correctness

`backend/commerce/money.js` parses decimal strings using BigInt and emits checked integer minor units. Unsupported precision is rejected instead of rounded. Line totals multiply exact minor units by bounded integer quantity; totals sum in BigInt and reject overflow. No live currency conversion occurs; only USD is accepted. USD-to-USD conversion is explicit zero. U.S. sales tax, domestic shipping, Algeria shipping and import duties remain unknown; both estimated delivered total and verified payable total are null. No weight, customs class or tax estimate is fabricated.

The ten-line regression (`tests/commerce-service.cjs:181`) uses five selections split across two merchant domains, quantities1–10 and a $0.29 price. Exact line sums total1,595 cents. The quote contains **one** conditional500-cent AnoX fee, independent of product/line count. No blocked attempt collects it. Affiliate rates/links are metadata rather than earned income. Refund tests verify monotonic principal and cap refunds at the expected amount; operational fee refunds, processing expenses and chargeback losses remain deliberately unclaimed and blocked by SEC-03/04.

## Limit profiling

Reproduce with `node scripts/profile-commerce-quotes.cjs`. The exact recorded simulation is `docs/remediation/quote-profile.json`; it uses no network, AWS SDK, credentials or financial calls. Five distinct selections with ten merchant lines generate five detail reads, with maximum concurrency3. Reads shared by the same product/options do not multiply per merchant.

| Simulated latency per detail read | Lines / distinct selections | Observed handler time | Outcome |
| --- | --- | --- | --- |
|100ms|1 / 1|105ms|201, one read/record/audit|
|100ms|10 / 5|206ms|201, five reads, peak3|
|1,000ms|10 / 5|2,004ms|201, five reads, peak3|
|4,000ms|10 / 5|8,003ms|201, five reads, peak3|
|5,000ms|10 / 5|9,005ms|503 deadline; no persisted record/audit|
|100ms|6 / 6|0ms|422 before any read|

These times exclude DynamoDB network/transaction latency, Lambda cold starts, provider throttling and billing. They show two waves of up to three reads, not actual service throughput. At four-second provider latency there is little headroom inside the nine-second hydration deadline, so raising five selections would be unjustified. The 10-line bound additionally limits serialized data and user review burden. A cart may store50 selections but quotes deliberately cannot validate all50 at once; the UI must disclose the lower quote limit. More than one quote does not authorize multiple service fees or create an order; the fee remains per successfully completed order under a future approved purchasing contract.
