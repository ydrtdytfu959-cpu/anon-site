# Algeria delivery-cost foundation and integration requirements

Reviewed October 13, 2026 against `feat/anox-commerce-foundation`, base `dd11ddedf277d74446d77af6836a67ee30abebf7`; the release manifest identifies the final revision. **Operational delivered-cost readiness: BLOCKED — EXTERNAL APPROVAL AND REQUIRED INPUTS.** No merchant shipment, carrier rate, insurance purchase or label was requested. Public documentation was read; the tests below are local contract fixtures, not carrier or AWS integration evidence.

The current customer quote preserves four unknown amounts: U.S. sales tax, domestic U.S. shipping, international shipping to Algeria and import charges. A fresh product price does not supply parcel dimensions, shipping eligibility, a customs classification or a merchant tax calculation. The USD quote has no currency conversion and one conditional 500-cent AnoX fee; neither a delivered estimate nor a payable total is synthesized. Checkout stays disabled.

## What changed in source

`backend/commerce/delivery.js` provides a small server-only contract for future approved adapters. `quote.js` uses its shared `deliveryComponents()` to construct the same unknown-component response as before. The commerce build includes this canonical module; generated CloudFormation must be rebuilt by `npm run build`.

- `DeliveryCostProvider` reports rates, insurance, labels and returns unavailable. Its `quote()` produces a stable `delivery_provider_unavailable` result, unknown components, and null totals. It performs no I/O and cannot enable purchasing.
- `validateDeliveryRequest()` accepts a server-established cart hash, immutable service/address/contents references, US origin, DZ destination, explicit delivery mode and measured parcels. It requires grams and millimetres as positive safe integers, rejects unrecognized units/fields, caps the representation at ten parcels, and canonicalizes parcel order. Representation ceilings are defensive bounds, not claims that a carrier accepts that package. The `serviceRef` must identify the approved carrier/account/service, tender date, payer and selected insurance/options; changing it invalidates the evidence hash.
- `validateDeliveryEvidence()` binds an authenticated future adapter result to its configured provider and the complete canonical request hash. It accepts only exact USD minor units, known component codes, explicit payer, proper ISO timestamps, bounded plain-text assumptions, and verified/estimated/unknown status. Omitted components remain unknown. Estimates require assumptions; unknown amounts cannot become zero. Duplicate components, malformed amounts, stale data, changed addresses/contents/service, arbitrary provider identity and response diagnostics fail with sanitized 503.
- Evidence observed30 seconds ago is already stale. A future provider expiry is capped to observation + 30 seconds; a shorter provider expiry wins. This is a conservative AnoX boundary, **not** a provider promise that its rate is fixed for30 seconds. Freshness alone does not make a rate guaranteed.
- Even an all-verified fixture returns null final totals and no checkout capability. “Verified” in this internal envelope means an adapter has substantiated that particular component under its reviewed contract; it does not prove full delivered-cost completeness, inventory reservation, commercial authorization or invoice finality. An estimated carrier response must remain estimated. No adapter currently supplies this envelope to customer quotes.

References must be dereferenced only server-side with customer ownership and immutable version checks. The current public quote API continues accepting only `{country:'DZ'}` for destination; it rejects new browser price/delivery fields. No new address collection, address persistence, PII logging, HTTP route or IAM access was added. The contract deliberately has no browser-controlled `verified` switch. A future adapter must be separately reviewed and cannot obtain authority merely by instantiating this class.

## Source evidence and limitations

EasyPost's Parcel contract uses ounces and inches with one decimal place. An adapter must explicitly convert the canonical measured grams/mm under reviewed rounding rules; passing grams directly as `weight` is incorrect. Shipment creation requires address/parcel evidence and may create provider objects, so it is not automatically an authorized free read. The release tests do not call it. [EasyPost Parcel](https://docs.easypost.com/docs/parcels), [Shipment](https://docs.easypost.com/docs/shipments), [Rate](https://docs.easypost.com/docs/shipments/rates).

Customs records require truthful goods descriptions, quantities, total values and weights, classification and origin. EasyPost distinguishes merchandise and other content types, signer/certification and return versus abandonment. Generating a customs form does not determine Algerian import liability or grant permission to import. [CustomsItem](https://docs.easypost.com/docs/customs-items), [CustomsInfo](https://docs.easypost.com/docs/customs-infos).

USPS lists material restrictions for Algeria, including used clothing/footwear/accessories and watches/clocks, and notes GXG suspension. These are reviewed restrictions, not a substitute for current rules for each SKU. The international alerts page retrieved for this report was updated October 2, 2026 and did not list Algeria in its country suspension table; absence from that list does not guarantee a particular parcel/service. Check both pages again before every operational route activation. [USPS Algeria conditions](https://pe.usps.com/text/imm/ab_003.htm), [USPS international alerts](https://about.usps.com/newsroom/service-alerts/international/welcome.htm).

UPS states billable weight can be the greater of actual and dimensional weight; the correct account/service guide must determine units, rounding and surcharges. FedEx explicitly describes rate output as estimates that can differ from the invoice and separately warns against inferring service availability from a rate response. AnoX therefore must not label a fresh quote “guaranteed” solely because it came from a carrier API. [UPS Algeria dimensions/weight](https://www.ups.com/dz/fr/support/shipping-support/shipping-dimensions-weight), [FedEx rate API](https://developer.fedex.com/api/en-us/catalog/rate/docs.html), [FedEx Algeria services](https://www.fedex.com/en-dz/shipping.html).

UPU identifies five-digit Algerian postcode structure and lists Algeria among countries requiring postcodes. Syntax validation does not validate a locality or prove deliverability. Algérie Poste's poste-restante and EMS pages indicate different fulfillment modes; service descriptions are not evidence that AnoX may promise those modes for its inbound lane. [UPU Algeria addressing](https://www.upu.int/UPU/media/upu/PostalEntitiesFiles/addressingUnit/dzaEn.pdf), [UPU postcode requirements](https://www.upu.int/UPU/media/upu/documents/PostCode/General-Addressing-Issues.pdf), [Algérie Poste FAQ](https://www.poste.dz/faqCC), [EMS service](https://www.poste.dz/customer/cor-ems).

Insurance and returns require separate provider states and customer responsibilities, not just a positive rate. A later implementation must verify signature/authenticity for notifications, distinguish pending from purchased/failed coverage, and reconcile reverse shipping independently from merchant payment refunds. [EasyPost Insurance](https://docs.easypost.com/docs/insurance), [EasyPost Returns](https://docs.easypost.com/docs/shipments/returns).

No alternative merchant, forwarder or aggregator is deemed approved by this report. USPS/UPS/FedEx are evaluated because the user requested them; EasyPost is the existing repository integration. No shipping tariff, tax rate, customs threshold or exact transit promise has been fabricated.

## Failure contracts and customer behavior

| Failure | Internal contract | Required customer outcome |
| --- | --- | --- |
| Missing, malformed or unsupported measurement/address/service input | `delivery_input_invalid`, 422; no provider call | Request reliable data or show the cost as unavailable; no guessed package size. |
| No approved adapter | Stable unavailable result with four unknown components | Preserve the existing unknown costs and disabled checkout. |
| Provider timeout, refusal, malformed body or missing/expired evidence | Future adapter maps to unavailable; validator returns sanitized `delivery_evidence_invalid`, 503 for invalid normalized evidence | Retain unknown cost, allow an explicit safe retry only under a separately reviewed provider budget. No synthetic fallback. |
| Missing component or unknown amount | Null amount/status unknown | Do not calculate a guaranteed delivered total or hide an arrival liability. |
| Changed cart, parcel, address, selected service/options or provider | Request hash mismatch, 503 at adapter boundary | Requote the exact new selection; do not transfer old evidence to it. |
| Carrier adjustment possible | Estimated component with explicit assumptions | Show estimate/possible later charges; do not collect a guaranteed total. |

The class does not implement retry, booking, purchasing, label cancellation or event handling. Those are **not hidden TODOs claiming completion**: they are explicitly absent capabilities requiring a separately approved adapter and commercial contract. Error messages never echo raw provider diagnostics or personal address data.

## Required acceptance evidence before connecting a real adapter

1. Approve one merchant-to-receiving-point-to-DZ route, participating account, seller/importer/payer roles, fee/refund obligations and a bounded test budget. Obtain actual contract/API schemas; keep production credentials server-side.
2. Supply measured packed parcels and immutable contents records, including correct manufacture origin and externally established classification. Catalog images/category labels are not sufficient evidence.
3. Verify at least one supported and one unsupported Algerian postcode, home and any authorized postal-pickup mode, and full recipient/origin address validation. Confirm carrier-specific prohibited items and current service alerts.
4. In an authorized sandbox, exercise malformed units/precision, missing dimensions, multiple parcels, changed measurements, currency mismatch, omitted surcharges, estimate-only output, expiry, no-rate responses and upstream timeouts. Prove no timeout creates duplicate paid objects.
5. Separately authorize real-provider reads to verify account-specific rates, serviceability, realistic latency, surcharges/insurance inclusion, explicit expiry, customs responsibility and carrier documentation. Mark fixtures, sandbox virtualization and real reads distinctly.
6. Before Release B, prove shipment/order/payment linkage, signature-verified notifications, failed-delivery escalation, claims/returns, label refund accounting, reconciliation and customer consent to any permitted arrival charges. The carrier contract—not an internal flag—must establish any guaranteed amount.

## Tests and review evidence

`tests/commerce-delivery.cjs` covers the disabled provider, unchanged unknown components, measured-unit bounds, canonical identity, explicit pickup choice, exact amounts, currency/precision/overflow rejection, malformed dates, the exact30-second stale boundary, wrong provider/cart/address/contents/service binding, estimate assumptions, duplicate/unsafe components, payer/arrival separation and permanent null final totals. All 15 local tests passed. Existing real quote/service/runtime tests passed with the extracted components. The first combined template run failed only because generated source had not yet been rebuilt; the root's final build/check supersedes this expected intermediate parity failure.

A self-review identified missing selected-service binding in the initial internal request contract. A regression for preserving the immutable `serviceRef` failed before correction, then passed with carrier/service/tender-date/insurance changes included in the canonical hash. The same review checked that no valid fixture can create a payable total or mutate input objects, and that a missing customs/tax component remains unknown. Independent cross-owner review and the final build/test results are recorded in the combined release evidence.

**Release A:** this foundation can be reviewed with checkout disabled and costs unknown; it supplies no live shipping claim. **Release B:** BLOCKED until authoritative merchant/parcel/tax/import/carrier inputs, authorization, complete payment/delivery responsibilities and real-service evidence exist.
